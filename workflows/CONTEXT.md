# workflows/

Standalone, local-only data-processing pipeline for job postings — independent of the FastAPI app and React dashboard. Scripts here connect directly to `sqlite:///auto_apply.db` (same pattern as `scripts/flag_failed_scrapes.py`: raw `create_engine`, no import of `db/database.py`'s app session factory) and are run via `python -m workflows.<script>`.

Goal: pull the scoring/generation "data processing" logic out of the UI-driven flow so it can be run and iterated on directly from the CLI.

## Files

- `fetch_recent_jobs.py` — step 1. Fetches the N most recently scraped jobs' raw text (`jobs.description` — already plain text, no HTML anywhere in the schema) and writes them to `workflows/output/` as JSON. `python -m workflows.fetch_recent_jobs --n 20`.
- `view_output.py` — renders a workflows JSON output file (default `workflows/output/recent_jobs.json`) into a static HTML page and serves `workflows/output/` on `http://localhost:8765` via the stdlib HTTP server (auto-opens a browser tab). No new dependencies, no connection to the FastAPI app. `python -m workflows.view_output`.
- `view_slides.py` — one-job-per-slide deck (arrow-key/button nav) for reviewing extraction quality: raw description column next to a processed/highlighted column, so it's visible exactly where each extracted field came from. Serves on `http://localhost:8766`. `python -m workflows.view_slides`. Supports A/B mode: `--compare-a <extracted_v1.json> --compare-b <extracted_v2.json>` renders a 3-column slide (raw | prompt A | prompt B) for comparing two extraction prompt versions side by side.
- `prompts/extraction_prompt.md` — the active extraction prompt used by the (currently manual) subagent extraction step. Deliberately separate from `prompts/defaults/extraction.md` (the live app's DB-seeded prompt) so it can be freely tuned without touching production. Extraction itself is run by dispatching a fresh subagent (cold-start, no conversation context) against this prompt + `workflows/output/recent_jobs.json`, writing `workflows/output/extracted.json` — this is not yet a standalone script.
- `prompts/history/` — snapshots of `extraction_prompt.md` taken before each edit during iteration, named `extraction_prompt_v{N}.md`. Keep only the 3 most recent; delete the oldest when adding a new one. Used for A/B comparisons via `view_slides.py --compare-a/--compare-b` (pair a history snapshot's extraction output against the current one).
- `fetch_profile.py` — pulls the local candidate profile (contact info, skills, work history, education, projects, target roles/salary) from `user_profile` for job-vs-candidate comparison and document rendering. Reuses `core.user.User.load()` against a locally-created engine/session (not the app's session factory) rather than re-implementing its JSON-blob hydration/legacy-tree migration in raw SQL. `python -m workflows.fetch_profile [--profile-id N]` → `workflows/output/profile.json`. Local DB currently has one real profile (id 9, DB row labeled "E2E Fixture" — a leftover from dev-login auto-provisioning, not test data) plus an unrelated `id 10` row from a resume-parse test; `--profile-id` disambiguates if that changes. **Known issue**: that same dev-provisioning also left placeholder `name`/`email` on this profile ("E2E Fixture" / `e2e-fixture@example.com`) — everything else (hero, skills, work history, education) is real, but the contact header on any rendered document is fake until the real profile is fixed in the dashboard.
- `prompts/compare_prompt.md` + `workflows/skill_match.py` — candidate-vs-job comparison: per-skill/per-requirement match level (direct/near/miss) with evidence, plus a 2-sentence fit summary. **Direct matches are pre-computed deterministically** before the subagent runs: `skill_match.precompute_direct_matches(job_skills, profile)` does a case-insensitive exact lookup against `profile.skills` and every project's `technologies` list, splitting the job's skills into `precomputed` (full skill_matches rows, ready as-is) and `remaining` (genuinely ambiguous — needs the subagent's near/miss judgment). Deliberately conservative: exact-match only, no substring/fuzzy matching (e.g. "OpenAI" doesn't auto-match profile's "OpenAI SDK" — left to the subagent rather than risk a false-positive like job-wants-"SQL" auto-matching profile's "SQL Server"). Dispatch instructions: give the subagent both lists, tell it to copy `precomputed` through unchanged and only judge `remaining`; `fit_summary` still sees the full picture so it reads coherently. Run by dispatching a fresh subagent against `extracted.json` + `profile.json` + the precompute output, writing `workflows/output/compared.json` (not yet a standalone script, same pattern as extraction). Verified: for a 22-skill job, `skill_matches` output still has exactly 22 rows (no drops/duplicates) and the 10 precomputed direct matches came through unchanged.
- `prompts/cover_prompt.md` — short, honest cover-letter generation, deliberately much shorter than the live app's `prompts/defaults/cover.md` (no fixed paragraph/word target — content dictates length, hard ceiling 150 words; plain/direct tone; enthusiasm implied through fit rather than stated). Includes a web-research fallback: when a job's `company_signals` are too thin to personalize from, the writing subagent uses WebSearch to find one concrete, current fact about the company before writing — this is why the dispatched subagent needs WebSearch tool access for this step, unlike extraction/compare which are pure text tasks. Run by dispatching a fresh subagent against `extracted.json` + `recent_jobs.json` (for company name) + `profile.json`, writing `workflows/output/cover_letters.json` ({letter, word_count, used_web_research, research_note} per job_key).
- `prompts/resume_prompt.md` — tailored résumé content: 1-2 sentence positioning summary, ordered/selected skills, work-history bullets rewritten per-job relevance (every entry always kept, for career continuity — only bullet count/wording varies), projects selectable (`include: true/false`) since unlike work history they aren't continuity-sensitive, education passed through verbatim. Deliberately scoped to the fixed sections `fetch_profile.py` pulls (Skills/Work History/Education/Projects) rather than the live app's fully generic profile_tree — a deliberate scope-narrowing decision for this local tool, revisit if custom sections are added to the profile. Run by dispatching a fresh subagent against `extracted.json` + `profile.json`, writing `workflows/output/resumes.json` ({summary, skills, work_history, projects, education} per job_key).
- `view_slides.py`'s processed column is tabbed whenever a job has a cover letter and/or resume: Description / Cover Letter / Resume (each tab disabled independently until its data file exists). Pass `--covers`/`--resumes`/`--resume-evals <path>` (defaults `workflows/output/cover_letters.json` / `resumes.json` / `resume_evals.json`) to wire them up; with none present the column renders untabbed as before. Tabs are per-column and independent of the raw↔processed bidirectional linking, which only targets the Description tab's content.
- `prompts/eval_prompt.md` + `workflows/resume_checks.py` + `workflows/eval_resume.py` — résumé eval, split between mechanical (Python, free, instant) and semantic (subagent) checks, `overall_pass` = AND of all six:
  - **Mechanical** (`resume_checks.py`, no LLM): `required_skills_covered` (case-insensitive substring search — does every genuinely-held, employer-**stated**, **direct**-match required skill appear somewhere in the résumé text?) and `no_continuity_errors` (diff — does every profile work-history entry survive, in order, with unchanged company/title/dates?). **Why these moved out of the subagent**: both are exactly the category of thing that produced a real bug when LLM-evaluated — the first version conflated "near" (transferable, not actually held) and "direct" matches, so PearSon's résumé kept failing on Flask/GPT-4/Transformers, which the candidate never used (fixed 2026-08-13, before the mechanical split). A deterministic check structurally cannot make that class of error. `required_skills_covered` is mandatory only for `compared.json`'s **stated + direct** matches — near matches and inferred skills are never mandatory (see below), matching the original design intent exactly. `resume_checks.required_direct_skills(compared_entry)` computes the filter (previously asked of a subagent by hand).
  - **Semantic** (`prompts/eval_prompt.md`, trimmed to 4 checks, subagent): `no_fabrication`, `no_keyword_stuffing`, `no_irrelevant_content`, `summary_specific` — genuine judgment calls that stay LLM-driven.
  - **Flow**: `python -m workflows.eval_resume <job_key>` runs the two mechanical checks and writes them to `scratch_path(job_key, "eval_mechanical")` (see `merge_utils.py` below), printing what's needed to dispatch the semantic subagent → that subagent `Write`s its 4-check result to `scratch_path(job_key, "eval_semantic")` (never touches `resume_evals.json` directly) → `python -m workflows.eval_resume <job_key> --finalize` combines both scratch files into the full 6-check shape and merges it into `resume_evals.json` via `merge_job_entry`. Output shape is unchanged from before the split (`{checks, overall_pass}` per job_key), so `view_slides.py`'s eval badge needed no changes. Verified: reproduces the known-good all-pass state for both jobs, and correctly flags deliberately-mutated résumés (dropped work-history entry, altered date, removed skill with a single occurrence).
  - `prompts/patch_prompt.md` — on any failing check (mechanical or semantic), dispatch a fresh subagent with only the failing checks' issues. Needs no structural change for the mechanical/semantic split — `failing_checks` already accepts whatever failed regardless of source.
  - `workflows/eval_loop.py` — the eval→patch decision loop as a state machine, since none of "is it passing, what failed, how many patch attempts so far, when to stop" is actually a judgment call. `python -m workflows.eval_loop <job_key> [--cap 3]` reads `resume_evals.json` + loop state (persisted at `scratch_path(job_key, "loop_state")`) and returns one of `{"action": "run_eval"}` / `{"action": "dispatch_patch", "turn", "failing_checks"}` / `{"action": "done", "result": "pass"}` / `{"action": "done", "result": "cap_reached", "remaining_issues"}`. It's a **driver Claude Code consults between dispatches**, not an autonomous loop — it can't call the `Agent` tool itself, only tell the caller what to do next. `--reset` clears a job's loop state. Verified: reports `pass` immediately for the current (already-passing) jobs; a simulated failing entry correctly produces `dispatch_patch` (turn 1, 2) then `cap_reached` at turn 3 with `--cap 2`.
- **Inferred (role-standard) skills** — `extraction_prompt.md` v4 added `source: "stated" | "inferred"` per skill: `"stated"` = employer literally named it in the JD; `"inferred"` = not named, but a near-universal expectation for that job title/responsibilities (e.g. Git for any software dev role — the extraction step is deliberately conservative here, only inferring skills that are genuinely standard, never speculative). This flows through the whole pipeline: `compare_prompt.md` downweights an inferred-skill miss in the fit summary (the employer never asked, so it's not a stated gap); `resume_prompt.md`/`cover_prompt.md` may feature a genuinely-held inferred skill but must never claim the employer asked for it; `eval_prompt.md`'s `required_skills_covered` check is mandatory **only** for direct-match **stated** skills — inferred skills (even direct matches) are never mandatory coverage, since the employer never asked for them. All five prompts were touched together in this pass; re-ran the full pipeline (extraction → compare → resume → eval → cover) for both jobs to keep them consistent — Genpact passed clean, PearSon caught and fixed a real gap (missing "Prompt Engineering," a genuinely stated+direct-matched skill) via the patch loop, distinct from the earlier direct/near false-positive bug.
- **Résumé skill grouping** — `resume_prompt.md`'s `skills` field is `[{"category", "items"}]`, not a flat list, capped at 5 categories with an explicit rule against singleton/near-empty categories (fold into a broader neighbor instead). Motivated by the Description tab's extraction categories often producing many one-item groups (accurate but not scannable) — the résumé is meant to be skimmed, so it needs coarser buckets than the analysis view. `view_slides.py`'s résumé panel renders the new nested shape but still falls back to rendering a flat list if an older `resumes.json` has one (backward compat for files generated before this change).
- `render_documents.py` — renders `resumes.json`/`cover_letters.json` to ATS-passing PDFs. **Deliberately breaks the "workflows/ never imports app internals" pattern** used by every other script here — it imports `core.document_assembler`, `core.schemas`, `core.utils.render_pdf`, and `core.ats_gate`, because those specific modules are pure/DB-free (no session, no DB import at all in `render_pdf`/`document_assembler`) and reusing them avoids reimplementing PDF rendering from scratch. Maps our JSON shapes onto the live app's `ResumeDocument`/`CoverDocument` Pydantic models (work-history/project `bullets` lists join into a single Markdown `description` string — `"\n".join(f"- {b}" for b in bullets)` for experience so pandoc's tight-list normalization recognizes it, `" ".join(bullets)` flowing prose for projects since `_projects_section`'s single-line `"**Name**: {description}"` join isn't list-safe), assembles canonical Markdown via `assemble_resume_markdown`/`assemble_cover_markdown`, then calls `core.utils.render_pdf` directly with an explicit `meta` dict (no YAML front-matter file needed — `render_pdf` accepts `meta` as a plain dict) against `generator/resume_template.html`/`cover_template.html` with the default "classic" theme (`css_path=None`). Runs the **mechanical-only** half of the live app's ATS gate (`core.ats_gate.extract_text` + `check_mechanical` — also pure, no DB/LLM) afterward, using `extracted.json`'s **stated** (not inferred) skills as the required/preferred lists, replicating `core.ats_gate.run_gate`'s score formula (`1.0 − 0.25·critical − 0.05·warning`) by hand since the LLM semantic round-trip layer (`check_roundtrip`) is intentionally not run here — it needs `core.llm`/an API client, which would break this step's local/offline-only property. Output: `workflows/output/pdfs/{job_key}_resume.{md,pdf}` and `{job_key}_cover.{md,pdf}`, plus `workflows/output/ats_reports.json` ({passed, score, issues} per job_key). `python -m workflows.render_documents` (no args, no LLM/subagent call — pure Python + pandoc + Chromium). Verified locally: both test jobs render single-page PDFs with ATS score 1.0, zero issues.
- `view_slides.py`'s Resume tab now shows an "Open résumé PDF" link (served from `workflows/output/pdfs/` by the same `http.server` instance) and an ATS badge (green pass w/ score, or red fail with itemized issues, each tagged `[mechanical]`/`[semantic]`) when `--ats-reports` data exists (default `workflows/output/ats_reports.json`); the Cover Letter tab gets an analogous PDF link. Both degrade silently (no link/badge) when `render_documents.py` hasn't been run yet.
- **Semantic ATS layer** — `prompts/ats_semantic_prompt.md` + `render_documents.py`'s `merge_semantic_issues()` add the second ATS-gate layer the live app calls `check_roundtrip`: a naive re-parse of the rendered PDF's extracted text (name/email/phone/sections), diffed against the document's real header/section_order, to catch cases where text is technically present but a real parser might misread it. Unlike the mechanical layer (pure Python, runs inside `render_documents.py` itself), this layer needs an LLM — dispatched as a **fresh subagent** (Claude Code orchestrates it, same pattern as the résumé eval/patch loop) rather than the live app's real API client, keeping this step billing-free and local. Flow: `render_documents.py` writes `{job_key}_resume_extracted.txt` (PDF text layer) and `{job_key}_resume_doc.json` (ground truth: header + section_order) into `workflows/output/pdfs/` → dispatch a subagent against `ats_semantic_prompt.md` + those two files per job → subagent `Write`s its issues list to `scratch_path(job_key, "ats_semantic")` (per the `merge_utils.py` convention — earlier runs had it inline a Python list literal into a `python -c` shell command instead, which works but is the same fragility class this convention exists to eliminate) → a follow-up call reads that scratch file and invokes `merge_semantic_issues(ats_reports_path, job_key, issues)` (idempotent, drops prior `layer: "semantic"` issues before appending fresh ones so re-runs don't accumulate duplicates) to fold results into `ats_reports.json`, recomputing `score`/`passed`. Semantic issues are always `severity: "warning"` by convention — this layer never hard-blocks, matching `core.ats_gate.check_roundtrip`. Verified on both test jobs: 0 semantic issues, clean roundtrip.
- **`workflows/merge_utils.py`** — shared-file merge primitives (`read_json`/`write_json`/`merge_job_entry`/`merge_job_entries`/`scratch_path`), and the standing convention for every step that touches a multi-job JSON file (`extracted.json`, `compared.json`, `resumes.json`, `resume_evals.json`, `cover_letters.json`, `ats_reports.json`). **Origin**: a patch subagent once wrote a literal `REPLACE_ME` placeholder over an untouched job's entry in `resumes.json` while patching a different job — it didn't actually read the full file first despite being told to. "Instruct it carefully" isn't a reliable fix for this; the structural fix is that **a subagent never opens a shared multi-job file at all**. Convention: the subagent writes its result for one job only to `scratch_path(job_key, suffix)` via the `Write` tool (no knowledge of any other job's data), then a separate deterministic call to `merge_job_entry`/`merge_job_entries` splices it into the real file. Used by `eval_resume.py` (eval scratch → `resume_evals.json`), the compare step (compare scratch → `compared.json`), and `render_documents.py`'s ATS-semantic dispatch (`merge_semantic_issues`, which now reads the subagent's scratch-file output rather than having the subagent inline a Python list literal into a `python -c` shell command — same fragility class, just via string-escaping instead of file I/O). Regression-tested directly: a two-job scratch file, merge one job's new content, assert the other job's entry is byte-identical to its original.
  - **Hardening (2026-08-17)**: the scratch-file convention isolates the *subagent* from the shared file, but not `merge_utils.py` itself from a caller bug or a malformed scratch payload. `write_json` now backs up the file's pre-write content to `backups/workflows/<name>.<UTC timestamp>.json` (gitignored, unpruned, matching the project's existing `backups/` convention) whenever the target already exists — the real recovery path if a bad write ever slips through again. `merge_job_entry`/`merge_job_entries` also validate each value before writing anything (`MergeValidationError` on a non-dict/empty value, or on a `"job_key"` field inside the payload that doesn't match the key being merged into) — batch merges via `merge_job_entries` validate every entry before any write, so a bad entry can't partially corrupt the file. The `job_key` field is optional in payloads (skipped when absent) so existing scratch producers keep working until their dispatch instructions are updated to self-identify. Tests: `tests/workflows/test_merge_utils.py`.
- The requirements behind `cover_prompt.md` came from a short interview (AskUserQuestion round covering length/structure, thin-content handling, tone, and enthusiasm framing) — this question set is itself a reusable artifact: the same questions could be offered to SaaS users to let them design their own cover-letter prompt/persona instead of one fixed house style.

## Human-in-the-loop gates

Claude Code is the orchestrator for this pipeline — only it can dispatch a
subagent, so scripts like `eval_loop.py` return an *action* for it to take
rather than taking it themselves. That makes "orchestrator agent" a role
Claude Code already plays every run, not a separate piece of software to
build. What's formalized here is *when* it stops and waits for the user's
approval before moving to the next stage, vs. when it proceeds on its own.

**Gate (stop and wait for approval) after:**
- **Compare** (`skill_match.py` + `compare_prompt.md`) — near/miss skill
  judgment calls; a wrong one skews everything downstream (résumé
  targeting, fit summary, eval's required-skills list).
- **Résumé/cover generation** (`resume_prompt.md`/`cover_prompt.md`) —
  content going out under the user's name; review in `view_slides.py`
  before proceeding to eval.
- **Eval hitting the patch cap** (`eval_loop.py`'s `cap_reached`) — the
  automated fix loop gave up; remaining issues need a human call, not
  another automated attempt.
- **Any `merge_utils.MergeValidationError`** — a scratch payload failed
  validation (empty/malformed value, or a self-identified `job_key`
  mismatch). This means something upstream is already behaving
  unexpectedly; don't paper over it by retrying blind.

**No gate (proceed automatically) for:**
- Mechanical/deterministic steps with no judgment surface: `merge_job_entry`/
  `merge_job_entries` writes, `resume_checks.py`'s two checks,
  `skill_match.precompute_direct_matches`, `render_documents.py`'s
  mechanical ATS layer (`core.ats_gate.check_mechanical`). These can only
  be *correct or buggy*, not judgment calls a review would catch — a test
  suite is the right check on them, not a per-run human gate.
- Passing evals (`eval_loop.py`'s `{"action": "done", "result": "pass"}`)
  and successful merges — nothing to approve.

The gate is a discipline Claude Code follows during a session, not a code
path — there is currently no script enforcing it. If pipeline runs start
skipping it in practice, that's the signal to build the enforcement (e.g.
extend `eval_loop.py`'s driver shape to cover cross-stage state so a
gated stage can't be silently stepped over), not before.

## Notes

- `workflows/output/` is gitignored — treat it as scratch data, not source.
- `jobs.description` is the only content column; scrapers (`scraper/`) and the browser extension (`browser-extension/content/`) both extract plain text before insert, so no HTML-to-text step is needed anywhere in this pipeline.
- Extraction prompt iteration loop: run extraction (fresh subagent) → review in `view_slides.py` → user lists what's wrong → snapshot current prompt to `prompts/history/` → edit `prompts/extraction_prompt.md` → re-run extraction to a new file → `view_slides.py --compare-a/--compare-b` to A/B the two versions.
